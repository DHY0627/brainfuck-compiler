# 自举：让 Brainfuck 写的编译器编译它自己

本文解释 `bfsrc/bfc2.bf` 的设计推理。它满足两条硬要求：

1. **输出的就是成品**：编译器向 stdout 写出**完整、可直接运行的 Windows exe
   字节流**，用户 `> prog.exe` 重定向即得可执行文件；
2. **不用任何外部工具**：链里没有汇编器、链接器、C 编译器——不调用 gcc。

`bfc2.bf` 能编译自己，且编译产物与上一代**逐字节相同**（自举固定点）。

## 1. 为什么"边读边写 + 机器码"看起来不可能

机器码里到处是**只能事后才知道**的值：

* `[` / `]` 的跳转位移——前向跳转的目标在看到 `]` 之前根本不知道；
* PE 头部字段：`SizeOfImage`、各节 `VirtualSize` / `SizeOfRawData`；
* 导入表 RVA、入口点 RVA——它们又依赖前面所有字节的长度。

只要输出是**流式**的（不能 seek 回退），就没有机会回头改写已经写出去的字节。
于是有三条路：

| 方案 | 做法 | 代价 |
|---|---|---|
| (a) 缓冲回填 | 产物先全放进磁带"寄存器"，最后一次性输出 | 磁带 O(程序大小)；被"直接输出到控制台"的要求禁止 |
| (b) 换结构化目标 | 输出 C 源码，`[`→`while(m[p]){`、`]`→`}` | 地址问题是没了，但要 gcc 才能变 exe——**不算自举** |
| (c) 推迟到运行期 | 输出**含地址占位符**的镜像，让 exe 自己启动时补上 | 需要一个能在 BF 里生成、几百字节的加载/补丁存根 |

`bfc0` 走 (a)，`bfc1` 走 (b)，`bfc2` 走 (c)。

## 2. PAK：把"回填"推迟到程序启动

关键在于：**PE 加载器允许文件末尾有任意数据（overlay）**，而 overlay 不需要
出现在任何节的 `SizeOfRawData` 里。于是：

```
文件偏移 0x0000  ┌──────────────────────────────┐
                 │ DOS + PE 头（0x200）          │
        0x0200   │ .rdata：导入表（raw 0x200）    │  RVA 0x1000
        0x0400   │ .text：入口存根（raw 0x400）   │  RVA 0x2000，RWX，
                 │        VirtualSize 0x2FE000   │  加载器把 VirtualSize
        0x0800   ├──────────────────────────────┤  - RawSize 的部分零填充
                 │ overlay：记录流 + 0 字节对齐   │  ← 变长，加载器不检查
                 └──────────────────────────────┘
```

* 头部是**固定 2048 字节常量**，与源程序无关；
* 记录流（编译产物）作为 overlay 追加在后，长度随程序变化；
* `.text` 声明了 3 MB 的 `VirtualSize` 却只有 1 KB raw 数据——加载器会把
  其余部分**填零**（这是 PE 规范行为，与"raw 超出文件末尾"完全不同，后者
  加载器会直接拒绝，`[WinError 193]`）。

程序真正执行时，`.text` 里那 627 字节的**自读存根**做五件事：

1. `GetModuleFileNameA` + `CreateFileA` + `ReadFile`：把自己的文件读进
   `0x6000`（2 MiB 上限）；
2. **入口校验**：文件必须至少有 `0x800` 字节（含记录流），且不许长于 2 MiB
   （多读 1 字节探测；超长就会被截断，拒绝执行）；
3. **补丁遍历**：从 overlay 起点线性扫描记录，遇到 `[` 压栈、遇到 `]` 弹栈，
   把两边的 `rel32` 跳转位移写成正确值；同时校验括号配平与嵌套深度；
4. `GetStdHandle(-11/-10)` 取出 stdout / stdin；
5. `jmp` 到第一条记录。

也就是说：**编译期只写占位符，运行期（进程内、几微秒）才把地址补上**。
BF 端因此只需要"逐字节抄写常量"，不需要任何算术或前瞻。

存根发现载荷不可执行时**不会运行垃圾字节**，而是带特定退出码直接退出：

| 退出码 | 含义 |
|---|---|
| 1 | 读不到自己的文件（被删除、无读权限） |
| 2 | 记录流超过 2 MiB 读缓冲（会被截断） |
| 3 | 循环嵌套超过 4096 层 |
| 4 | 多余的 `]` |
| 5 | 未闭合的 `[` |
| 6 | 文件短于记录流起点（没有载荷） |

## 3. 记录格式

每条记录 = `[长度][类型][payload][EB 02]`。末尾的 `EB 02` 是 `jmp +2`，
正好跳过**下一条记录**的 2 字节头，落到它的 payload 上——这样所有记录可以
紧挨着排，执行流自然串联。

| 指令 | 记录长度 | payload |
|---|---|---|
| `+` | 6 | `FE 03`（`inc byte [rbx]`） |
| `-` | 6 | `FE 0B` |
| `>` | 6 | `48 FF C3`（`inc rbx`） |
| `<` | 6 | `48 FF CB` |
| `.` | 36 | `mov al,[rbx]` / `mov [r15],al` / `WriteFile(stdout, buf, 1, &written)` |
| `,` | 42 | `ReadFile(stdin, buf, 1, &nread)` / `getchar` 语义（EOF 写 0） |
| `[` | 13 | `cmp byte [rbx],0` + `0F 84 rel32`（je 占位） |
| `]` | 13 | `cmp byte [rbx],0` + `0F 85 rel32`（jne 占位） |
| 结束 | 18 | `ExitProcess(0)` |

`[` 与 `]` 的 `rel32` 位置固定（`rec+7`），存根据此回填；目标地址由记录边界
直接算出（`]` 之后的下一条记录 payload、`[` 之后的下一条记录 payload）。
所有对外部数据的引用都是绝对地址（映像固定加载在 `0x140000000`，关闭 ASLR），
所以记录内容与它所在的位置无关——这让 BF 端可以无脑抄模板。

## 4. 自举链（`bootstrap/selfhost_pak.py`，29 项检查）

```
bfc.exe                    (C++ 种子，手写机器码 + 手工 PE)
  │  编译 bfsrc/bfc2.bf（79455 字节纯 BF）
  ▼
bfc2_seed.exe              (BF 编译器翻译成的原生程序)              0.017 s
  │  bfc2_seed.exe < bfsrc/bfc2.bf
  ▼
bfc2.exe                   (编译器编译自己 → 576523 字节 exe)      0.316 s
  │  bfc2.exe < bfsrc/bfc2.bf
  ▼
stage3.exe                 (新编译器再次编译自己)                  2.468 s
```

**固定点**：`stage3.exe` 与 `bfc2.exe` **逐字节相同**。从这一步起，
"编译器的编译器"与"编译器"产出的可执行文件完全一致——这是自举成立的定义性
检查。`bfc2.exe` 与 Python 参考模型（`tools/pak.py`）逐字节相同，所以上面
每一步都不是"看起来对"，而是被独立模型钉死的。

注意链条里**没有 gcc**：`bfc.exe` 只是把 BF 源码翻译成机器码的种子，
之后所有 exe 都是 Brainfuck 程序自己写出的字节流。

## 5. 验证

```bat
python tools\verify_bfc2.py        :: 在 Python 里解释 bfc2.bf：11 个用例与模型逐字节一致
python tools\test_pak.py           :: 34 项：5 个示例的 stdout/退出码与 bfc.exe 产物一致、
                                   ::      PE 结构、6 种坏载荷的拒绝退出码
python tools\test_pak_large.py     :: 6 项：把 48 KB 的 awib.b 编译成 384638 字节 exe，
                                   ::      对 6 组输入与原生 awib.exe 输出逐字节相同
python bootstrap\selfhost_pak.py   :: 29 项：完整自举链 + 固定点 + 示例程序 + awib
```

* `tests/pecheck.py`（独立 PE32+ 结构校验器）对 PAK 镜像返回 `errors: []`：
  节表、导入表、IAT 目录、对齐全部合法。
* 编译产物与 `bfc.exe` 直接编译同一 BF 程序得到的 exe **运行行为一致**
  （stdout、退出码），包括 `cat` 这种交互程序。
* 大程序回归：把 48535 字节的 awib 源码编译成 384638 字节的 exe，再拿它跑
  awib 自带 `systest`，结果与原生 awib 逐字节相同。

## 6. 限界

* 记录流上限 **2 MiB**（`.text` 的读缓冲），约合 **34.9 万条** `+`/`-`/`>`/`<`
  （每条 6 字节），或 5.8 万条 `.`（每条 36 字节）；`bfc2.exe` 自己 576 KB、
  awib 384 KB，都在这条线以内。
* 循环嵌套上限 **4096 层**（补丁栈大小）。
* 磁带 30000 个 8 位单元（与 `bfc.exe` 默认一致）。
* 载荷不可执行时由存根带退出码拒绝（见 §2 表），**不会**运行到越界/悬空跳转。
* 只有 Windows x86-64；程序启动时多一次自读 + 补丁（几十微秒），运行期比
  `bfc.exe` 产物慢约 1.5–3 倍（每条 BF 指令多一个 `jmp`）。
* 输出仍是"记录流"，不追求最小体积：`+` 占 6 字节而非 2 字节，换来的是
  编译器端零算术。

## 7. 走过的弯路（值得记下的两个教训）

1. **不能让 `SizeOfRawData` 超过文件末尾**。曾把示例 exe 的最后一节声明成
   1 MB raw 数据而文件只有 35 KB，结果加载器直接报
   `[WinError 193] 不是有效的 Win32 应用程序`。可用的做法是反向的：
   `VirtualSize` 大、`RawSize` 小（零填充），外加 overlay。
2. **先用 C 目标把自举跑通是很值的一步**（`bfc1`，见
   `bootstrap/selfhost.py`）。它证明了"流式输出 + 固定点"这套骨架是对的，
   也暴露出 BF 端真正需要的只是"抄常量"；后来换回机器码目标时，骨架几乎
   原样复用，只把模板换成记录字节。

## 8. 与 awib、bfc0 的关系

* `bfc0`：BF → 机器码，但**缓冲回填**、不支持循环，不能自举；
* `bfc1`：BF → C，靠 gcc 出 exe，能自举，但"用了 gcc"；
* `bfc2`：BF → 完整 exe 字节，**不用任何外部工具**，能自举；
* [awib](https://github.com/matslina/awib)：同样用"流式输出 + 定长编码"解决
  回填问题（它的 386 后端用 `rel32` 强制定长、靠预扫描求长度），但目标选
  ELF/C 等文本或结构化格式；`bfc2` 把同样的思路用在 PE 上，并额外引入
  运行期补丁存根，从而不需要预扫描求和。
